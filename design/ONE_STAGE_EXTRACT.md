# 一段式抽取设计（ONE_STAGE_EXTRACT）

> 状态：设计决议 · 2026-11-11 · **待实现**（现行代码仍是两段式：`lib/trigger-scan.ts` → `lib/knowledge-extract.ts`）
> 取代：TRIGGER_PLAN 的"抽取触发机制（扫描出候选）→ 知识抽取（候选原文出卡片）"两段式
> 术语：知识卡片 / 准入规则 / 主题 / 短效知识 沿用全库统一叫法
> 一句话：**一次 LLM 调用同时做完"检测有没有货 + 写成卡片 + 定性 + 记 drop"，省掉独立扫描那一趟；保真度靠分级压缩和按需回读补，审计靠强制 drop 账补。**

---

## 一、为什么改（取舍记录）

两段式的实测账单（TRIGGER_PLAN §4.6，855 条消息的真实会话）：

| 项 | 实测 |
|---|---|
| 输入 token | 79,467 |
| 输出 token | **156,122（输入的 2 倍）** |
| 原因 | 推理型模型的思考 token 计入 completion；有一批只标了 11 条候选却产生 31,333 输出 token |

独立扫描这一趟的全部产出只是"哪几条可能有货 + 一句理由"，却花掉了整个管线最贵的一笔。**扫描的成本主因是推理 token，不是输入**（TRIGGER_PLAN §十七 已诊断），而它的产出信息量极低——这是典型的成本与产出不匹配。

一段式把两趟合成一趟，预期总成本降到两段式的 50–60%，代码少一层（无候选中间态、无两段编排）。

> 这个 50–60% 是**沿用推理模型**前提下的估算（§5.2 已决）：省掉的是"同一批内容被推理两遍"，不是把模型换成便宜档。所以它是估算不是承诺，最终以验收 §七#2（总 token ≤ 两段式的 60%）为准；若不达标，杠杆依次是批次体积、prompt 缓存命中、再才是模型档位。

**外部佐证**：billion-context（`github.com/ranxianglei/billion-context`，上下文压缩代理）踩过同一个坑，并把结论写进了提示词——`ONE_CALL_HINT`（其 issue #2302）：一个 555K 的会话分 5 次单区间调用压缩，耗时 44 秒、**重复计费 1.38M tokens**，于是写死 "ONE call, ONE string … never split the batch"。

**代价与对策**（每一条都必须落实，否则一段式会退化）：

| 代价 | 对策 | 落在哪一节 |
|---|---|---|
| 压缩视图写卡片，命令/报错残缺 | 分级压缩：放宽命令行与 stderr，继续压 stdout | §三 |
| 高保真需求无法满足 | 按需回读（模型自己声明要原文，才补一趟） | §三.4 |
| 漏检不可见（没有"看了没抽"的记录） | 强制 drop 账，缺账视为不合格输出 | §四.2 |
| 目标函数滑向 summary（均衡要点、概括 AI 自己的话） | prompt 显式反摘要禁令 + 反例 few-shot + 验收第 5 条盲评 | §四.1、§七 |
| 固定 30 条窗口切断上下文（第 12 条的方案 + 第 31 条的纠正分家） | 批次按会话轮次边界对齐 + 窗口重叠 | §二 |

## 二、批次怎么切

**不按"每 30 条消息"死板切**，按下面三条规则成批：

1. **轮次不可分**：一轮对话（用户消息 → 助手回复 → 该轮所有工具调用与结果）是原子单位，绝不切开。切开就会把"纠正"和它针对的"方案"分到两批，两边都看不出价值。
2. **成批阈值（2026-11-11 决议：只看这两个，取消"距上次 ≥10 分钟"的时间下限）**：累计未覆盖消息 **≥30 条**，**或**压缩后体积 **≥12k token**——任一满足即成批。
   - 不需要时间下限的原因：跑完一批，覆盖水位前移、待审归零，下一条要等再攒够 30 条——**30 条门槛本身就防抖**；并发由 `pipelineRunning` 挡住
   - 两个条件的分工：30 条防"批太碎"（调用次数多、固定开销摊不薄），12k token 防"批太大"（一轮里有超长工具输出时，条数没到但体积已到）
   - 不满 30 条的尾巴由 **② 任务收尾**（完成 / 退出 / commit / 空闲）兜底，不再靠定时器
3. **窗口重叠**：每批额外带上一批**最后 1 轮**作为只读上下文（标 `readonly: true`，不重复抽），用于跨批引用。

覆盖率由**代码记账**（喂进批次的消息即视为已审），不依赖模型自报——这条沿用现有 `lib/coverage.ts`，不改。

## 三、输入怎么构造（分级压缩）

### 3.1 压缩规则（相对两段式的修订）

| 内容 | 喂给模型的 | 相对旧规则 | 理由 |
|---|---|---|---|
| 用户消息 | 全文 | 不变 | P0 主产地，只占 0.4% 体积 |
| 助手最终回复 | 全文 | 不变 | 决策、结论、被否方案都在这 |
| 助手中间消息 | 首尾各 500 字 | 不变 | 平均 141 字，基本等于不截断 |
| **工具参数（命令行）** | **完整命令行，上限 2000 字**；超限触发 fail-safe 整条透传 | **从"前 80 字"放宽到 2000** | `sop` 卡的核心是"到底跑了什么"，截断后不可复现。上限取 2000 是实测定的：143 条命令中位 579 字、P90 2477 字，600 会截掉一半命令，每条截断都换来整条助手消息按 4000 字透传 |
| **工具参数（写文件的正文）** | **上限 600 字**，超限只标"内容截断"，**不触发透传** | 新增分档 | `write`/`edit` 的 content 是文件正文不是命令，截断只损失篇幅、不影响可复现性。不分档的代价实测过：98/522 条（19%）触发透传，远超验收 #8 的 5% 阈值，透传的全是文件正文 |
| **工具参数（结构化 JSON/YAML）** | 键名 + 前 80 字 | 不变 | 重复的结构化参数是体积大头、价值低 |
| **工具结果（失败或有 stderr）** | **stderr / 报错行全文（上限 800 字）** + 首行 + 长度 | **从"只留首行"放宽** | `postmortem` 卡的"现象"字段必须是报错原文，不能是转述 |
| 工具结果（成功且无 stderr） | 首行 + 成功标记 + 长度 | 不变 | stdout 是体积大头、价值低 |

**修订原则一句话**：放宽的都是**小体积高价值**部分（命令行、stderr），继续压的都是**大体积低价值**部分（stdout、重复 JSON 参数）。实测那 397k 字符的工具参数里，绝大部分是重复的结构化参数，命令行本身很短——所以这次放宽对总输入的影响有限，但对 P1 卡片的保真度是决定性的。

### 3.1.1 fail-safe 断言：报错行丢了，这条就不压

借鉴 billion-context `crush` 的 `log-select` 硬约束——"每条 ERROR/FAIL 行必须逐字存活，否则整体拒绝、原文透传"。压缩后必须通过断言，**否则该条工具结果原样透传、不压**：

- 原文里每一行 stderr、以及含 `ERROR` / `FAIL` / `error:` / `Exception` / `Traceback` / `fatal` 的行，压缩后必须逐字存在
- 命令行必须完整（没被 2000 字上限截断），否则该条透传。**写文件的正文被截断不算**——只有 `command`/`cmd`/`script`/`sql` 这类真命令、或 shell 类工具的参数才触发透传（实测把透传率从 19% 降到 3.8%）
- 断言失败记 `compress_fallback` 计数进运行账本；持续偏高说明上限设小了——调上限，不是放宽断言（2026-11-12 已按此把命令上限从 600 调到 2000，透传率 19% → 3.8%）

理由：报错原文是 `postmortem` 卡"现象"字段的唯一来源，也是将来 grep 的抓手。宁可这一条不省钱，也不能让卡片里的报错变成转述。

### 3.1.2 压缩占位符要带"取回凭证"

被压掉的大块内容不能只留"首行 + 长度"——那样模型看不出这里丢了什么，也就无法申请回读（§3.4）。改为带句柄的占位符（借鉴 billion-context 的 ccr）：

```
📦 [压掉 #m00423 · shell 输出 · 原 12,345 tok · 已保留 stderr 3 行] `pnpm test --filter core`
   → 需要原文时在 need_context 里报 m00423
```

四要素缺一不可：**msg_id + 内容类型 + 原始体积 + 命令/文件名**，外加"保留了什么"。这样模型的 `need_context` 才有的放矢，而不是盲目申请回读。

### 3.1.3 净收益检查：压完不比原文小就不压

实现时发现的一个真问题：**小消息压不动，但前缀（`[User m00123]`）、占位符、"✅ N 字"这些元数据是净增的**——一批全是短消息时，压缩后的体积可能反超原文（实测构造用例 ratio = 1.014）。

规则：逐条比较"压缩后正文"与"原文"，**压缩后不比原文小 → 直接用原文**（仍受 hardCap 4000 字保护），并记 `noGain`。借鉴的正是 billion-context 的 net-benefit gate（摘要不比原文小就拒）。

`compressStats()` 同时报 `fallback`（fail-safe 透传）与 `noGain`（净收益不足）两个计数，进运行账本。

### 3.1.4 输入构造的两个前置 bug（2026-11-12 实测抓到并修）

压缩规则再精细，前提是**内容先进得来**。第一次端到端校准时发现两个 bug，都在旧代码里就有、新模块照抄了同一个形状假设：

| bug | 症状 | 根因 | 修法 |
|---|---|---|---|
| **工具事件整类丢失** | 288 条 entries 只序列化出 118 行；命令行 0 条、报错原文 0 条；`sop`/`postmortem`/`template`/`rubric` 四种类型整场没出现 | `lib/window.ts` 的 `normalizeDshEntry()` 只收 `user/message` 和 `assistant/message`，dsh 的 `tool/result` 事件（本会话 243 条）在解析阶段就被丢掉 | 收 `tool/result`，role 归一成 `toolResult`，工具名从同 callId 的 `tool/call` 关联，id 用 callId（可被 `msg_ids` 引用） |
| **工具调用块认不出** | 224 条助手消息里 170 条被整条跳过，剩下 54 条也只留正文、丢掉全部命令行 | `blocksOf()` 只认 pi 形状的 `type:"toolCall"` + 对象 arguments；dsh 是 `type:"tool-call"`（连字符）+ **JSON 字符串** arguments | 两种形状都认，字符串 arguments 先 `parseArgs()` 解析；`lib/trigger-scan.ts` 的 `blocksToText()` 同步修（保持 A/B 公平） |

修完实测：entries **288 → 525**（含 237 条工具结果），序列化 **118 → 522 行**，命令行 **0 → 189 条**、报错输出 **0 → 22 条**、成功输出 **0 → 173 条**，压缩比 0.517 → **0.389**（原文 98k → 635k 字符，压缩后 206k → 247k）。批次数 5 → **18**。

**连带影响（知情项，2026-11-12 核过）**：

- **CLI / dsh 路径**：entries 涨 82%（288→525），同一会话的批次数从 5 涨到 18。`adapter-dsh` spawn 时带 `--max-batches 3 --budget 60000`，所以单次调用覆盖的比例变小，但覆盖水位会推进、下次接着跑，能自愈。
- **adapter-pi 进程内路径不受影响**：它数的是 pi 宿主 `sessionManager.getEntries()` 的活消息（pi 本来就把工具结果作为 `role:"toolResult"` 的独立 message 给出），**不经过 `parseSession`**。所以"待审 ≥30 条"这个触发阈值的语义没变，不需要重新拍。
- 覆盖水位按 msg_id 记账，两边都不受影响。

回归用例锁在 `scripts/smoke-one-stage.ts` 第 2、9 节（两种形状 + parseSession 收工具事件）。


### 3.2 分级压缩对价值级的影响（为什么这样放宽就够）

| 价值级 | 内容住在哪 | 一段式（压缩视图）损失 |
|---|---|---|
| P0 人纠正模型 / 决策 + 被否方案 | 用户消息 + 助手最终回复 | **无损**（两者都全文保留） |
| P1 现实验证 / 意外 | 工具参数、工具结果 | **修订后基本无损**（命令行 + stderr 保留） |
| P2 文档口径 | 文档线负责 | 与本管线无关 |
| P3 模型自说自话 | 助手中间消息 | 默认不抽，损失即收益 |

### 3.3 每批输入的组装顺序

```
[只读上下文：上一批最后 1 轮]        ← 标 readonly，禁止从中出卡
[本批轮次 1..N，按时间顺序]
  每轮内：用户消息 → 助手中间消息 → 工具调用（命令）→ 工具结果 → 助手最终回复
  每条带 msg_id（卡片 source 必须引用它）
[已有主题清单]                        ← 防主题被拆碎，模型必须优先从中选
[已知卡片摘要（可选，判重用）]         ← 同主题近期卡片标题列表，防重复出卡
```

### 3.4 按需回读（保真度兜底，**一期不做，二期按数据决定**）

模型输出卡片时可以带 `need_context: [msg_id...]`，声明"这几条我需要原文"。管线取回这些消息的**未压缩全文**，只针对它们补一趟调用。

这是两段式的**按需退化版**：默认一趟，只有模型自己判定信息不足时才补。预计触发率 <10% 批次。

**一期不做的理由**：先按 §3.1 的分级压缩跑，用验收第 4 条（P1 卡片逐字接地合格率 ≥90%）量一下——达标就不用回读，不达标再开。避免为未验证的问题提前加复杂度。

## 四、输出契约

### 4.1 Prompt 结构（system，按顺序）

1. **角色与目标函数**：你是知识**筛选器**，不是摘要器。目标不是覆盖这段对话说了什么，而是找出"以后还能照着做 / 照着判断"的极少数内容。**大部分批次输出 0 张卡片是正常的**，硬凑卡片是失败。
2. **三条判定轴**（稀缺性 / 验证性 / 复现性，任一为零 → 进 drop 账，不出卡）
3. **价值分级**：P0 人→模型 > P1 世界→模型 > P2 文档→模型 > **P3 模型独立生成默认不抽**；明写"流畅、专业、漂亮都不是证据"
4. **六类高价值正向清单**（C1 否定与修正 / C2 决策及理由 / C3 被验证的经验事实 / C4 人的领域知识外溢 / C5 预期违背 / C6 会话间复现的隐性上下文）
5. **负面清单**（模型背书复述、通用建议、未验证猜测、执行流水账、寒暄与格式调整）
6. **反摘要显式禁令**（这一段是防退化的关键）：
   - 不要叙述对话流程（"用户问了 X，助手答了 Y"）
   - 不要为每个话题都产一条
   - 不要概括助手的解释性长文
   - 每张卡必须能回答"下次遇到同样情况，该怎么做 / 怎么判断"
7. **8 类型定义 + 各类型必填字段**（沿用 `DOC_TYPE_SPEC`，不新增类型）
8. **接地要求**：`quote` 必须逐字来自 `source.msg_ids` 的原文，不许改写、不许拼接；写不出逐字引用就说明接地不足 → 进 drop
9. **逐字保留清单**（借鉴 billion-context `HOW_TO_COMPRESS_RULES` 的 KEEP VERBATIM，其头注写明"数月生产调优、每个字段都 load-bearing"）：
   - 完整文件路径**带行号**（`lib/hooks.ts:347`），禁止缩写成裸文件名——裸名无法 grep、无法回读
   - 函数 / 类 / 类型签名，以及**"就是结论的那一行代码"**（不只是函数名）
   - 报错与堆栈**逐字**（要能拿这个字面串去搜）
   - 精确值：版本号、配置键、阈值、magic number
   - 发现的约束（"必须支持 Node 22""不许加新依赖"）
   - **数字 + 机制，不要光结论**：写"KV 缓存是静态的，所以困惑度差 1.76 倍"，不写"KVNet 效果不好"
   - **决策必须带"因为"**：`chose X over Y because Z`——没有 because 的决策看起来像瞎定的
   - 死路只留一行：`试过 X，因为 Y 失败`
10. **引用的两条规矩**：
    - 用户原话必须带 `msg_id`；**没有可验证 ref 就只能写"大意是…"（paraphrased）**，绝不许把半记得的话当成逐字引用
    - **引用是历史记录，不是活指令**：卡片会被编译进技能正文、被未来的 agent 读到，所以历史内容必须写成历史（"当时定的是先 A 再 B"），**禁止写成祈使句**（"要先 A 再 B"）。billion-context 的生产事故 #309 就是一句伪造的用户原话被当成活体 CURRENT TASK，导致循环复发
11. **风格约束**：写密集可扫的要点，不写叙述性散文；**不要模仿输入里"已知卡片摘要"的写法**（那是给判重用的，不是范文）；不要把工具输出里的 `\uXXXX` 转义序列抄进卡片
12. **优先级**（正文预算不够时按此顺序保留）：目标与硬约束 > 决策及理由 > 精确技术物（路径/签名/报错/数值）> 结论与关键发现 > 教训
13. **输出 JSON schema**（见 4.2）
14. **few-shot 各一例**：
    - 正例：用户说"不对，反了，应该先 A 再 B" → `postmortem` 卡，quote 逐字，grounding=G1
    - **反例**：助手输出一段结构漂亮的架构讲解 → `drop`，reason=P3 自说自话，axis=验证性=0

反例 few-shot 直接压制 summary 偏移，不可省。

### 4.2 输出 JSON

```json
{
  "cards": [
    {
      "type": "sop|spec|template|case|postmortem|convention|index|rubric",
      "title": "≤30 字",
      "body": "卡片正文，按类型必填字段组织",
      "why_lose": "≥8 字：不存会损失什么",
      "expires_when": "convention / index 必填，其他类型可选",
      "domain": "kebab-case，优先从已有主题清单里选",
      "source": { "msg_ids": ["..."], "quote": "逐字引用 ≤120 字" },
      "grounding": "G1|G2|G3|G4",
      "value": "P0|P1|P2",
      "need_context": ["msg_id"]
    }
  ],
  "drops": [
    {
      "msg_ids": ["..."],
      "reason": "可再生|无动作改变|说不清损失|P3自说自话|已有重复|纯流水账",
      "axis": "稀缺性=0|验证性=0|复现性=0|—"
    }
  ],
  "no_value": false
}
```

**三个强制约束**：

- `cards` 可以为空，但 **`drops` 或 `no_value: true` 必须有一个**——"看了没抽"必须留痕。缺账的输出视为不合格（见 §五）。
- `value` 不允许填 `P3`：P3 一律进 drops。这是把"P3 默认不抽"从建议变成契约。
- **每一条 `[User ...]` 消息都必须有归属**：要么进某张卡的 `source.msg_ids`，要么进某条 `drops` 的 `msg_ids`。用户消息是"人的纠正"和"决策理由"的主要载体，静默跳过视为不合格输出（重跑一次；重跑仍缺由代码兜底补账，见 §4.3）。同类消息可以合并进同一条 drop 的 `msg_ids`，不必一条一行。助手消息与工具输出**不**要求逐条交代（量太大，只统计 `unaccounted` 作观测指标）。

**第四个约束在代码侧（不靠模型自报）**：**摘抄率**过高 → 判为"摘抄不是提炼"，准入拒绝。摘抄率 = `copyRatio(原文, 正文)`，即**正文的 16 字碎片有多大比例逐字出现在 `msg_range` 的原文里**；阈值 `COPY_RATIO_MAX = 0.6`，正文不足 100 字的短卡豁免（`OVERLAP_MIN_BODY_CHARS`）。对应 billion-context 的 net-benefit gate（摘要不比原文小就拒，回执 "distill harder next time"）。这是能常驻的零成本反摘要闸门，比人工盲评便宜得多。

> 🔧 **这个闸门的方向写反过一次（2026-11-12 操作型会话抓到，已修）**。旧实现算的是"`quote` 的碎片有多少落在正文里"，方向正好相反，后果是双重的：
>
> 1. **短引用必死**：quote ≤16 字时旧实现直接 `return body.includes(quote) ? 1 : 0`。模型引一句 4 个字的用户原话、自己写 356 字分析 → 判 100% 摘抄。
> 2. **量错了对象**：反摘要要问的是"正文有多少是抄来的"，不是"引用有多少被正文包含"。
>
> 实测代价：那一轮 6 张被拒卡片里 **5 张是这个闸门拒的**，它们的真实摘抄率是 **5% / 10% / 13% / 20% / 38%**，全在阈值内；其中 4 张是 P0/P1（过滤方案决策链、全量重判改选方案B 的理由、搜索范围纠正、冒烟测试两个前置坑）。同一批 49 张落库卡的真实摘抄率中位 32%、最大 46%——**改成正确方向后 0 张落库卡会被拦，5 张误杀全部回收**。这张闸门当时一张真摘抄都没抓到。
>
> 比对对象也一并从"模型自己挑的那句 `quote`"换成"`msg_range` 内的全部原文"：只比 quote 太窄，正文可以抄区间内别处绕过闸门。
>
> 函数因此改名为 `copyRatio(source, body)`、闸门选项改名 `copyRatio`、常量改名 `COPY_RATIO_MAX`——**名字必须自带方向**，这个 bug 就是 `overlapRatio(body, quote)` 这个中性名字骗人造成的（参数顺序换了语义就反了，而调用点看不出来）。

### 4.3 drop 账的粒度

**已决（2026-11-12）：混合粒度**——按被放弃的价值候选记，但 **user 消息例外，必须逐条有归属**。

原来的"只按价值候选记"实测有洞：抓到两条 P0 用户消息（一条是三项架构决策"还是按类型分档 / 用同一个模型 / 走提案"，一条是术语纠正"结晶这个词太术语了"）确实进了批次、按规则全文未压缩，模型却**既没出卡、也没记 drop**——静默忽略了。契约原先只要求 `drops` 非空，管不住这种情况，所以验收 #2 显示 ✅ 是假的（它查的是"每批有没有 drop"，不是"每条消息有没有交代"）。

三层防线：

1. **契约层**：prompt 明确"每条 `[User ...]` 消息必须进 cards 或 drops"，缺了判不合格
2. **重跑层**：不合格重跑一次（veto 边界不变：模型声明 `no_value` 绝不重跑，那是行使否决权）
3. **代码兜底层**：重跑后仍缺，就把这些 user 消息 id 自动补成 drop 记录，`reason="模型未申报"`、`axis="—"`，与模型自报的理由区分开，便于事后统计漏检率；同时计 `autoDropped` 进运行账本
4. **准入之后收口层（2026-11-12 新增）**：上面三层只管到"模型输出"为止，管不到后面。实测抓到新洞——模型把 3 条 user 消息（含 2 条 P0 探针）正常写进了卡片，**卡片却被准入闸门拒了**，于是这些消息变成"既没卡也没 drop 行"的孤儿，账面上看着交代过、实际知识丢了。现在每批结束时复查一次：批内 user 消息若既不在任何落库卡片的 `msg_range` 内、也没被模型 drop，就补一行 `reason="卡片被拒：<拒因>"`，计入 `orphanedByReject`。

   > 这个指标本身也是**闸门健康度的报警器**：`orphanedByReject > 0` 意味着"闸门拒掉了带用户原话的卡"，要么卡片确实该拒（那用户消息的价值也随之消失，记账即可），要么闸门在误杀（那就该去看 `extract-rejected.jsonl` 的全文）。上面那个方向写反的 bug，就是靠追这 3 条孤儿消息挖出来的。

兜底有一条硬约束：**只在 JSON 解析成功时才补**。JSON 都没解析出来时"未交代"等于全部消息，补账就把整批伪造成"已审过"并推进水位，那批消息会永久丢失——这种情况保持不合格、不推进水位、下次重扫。

判断标准仍是：这段内容"看起来像知识但被放弃"才记 drop；纯寒暄、格式调整归入一条 `reason=纯流水账` 的聚合 drop。

drop 账落 `extract-drops.jsonl`，用途：①算漏检（人工抽样复核 drop 是否误杀）②调 prompt（哪类 reason 占比异常）③回答"覆盖率 100% 但召回够不够"。

## 五、触发、预算、失败降级

### 5.1 触发与节流（节流条件已改，其余沿用现有）

- **节流只看量，不看时间**（2026-11-11 决议）：待审消息 ≥30 条 **或** 压缩后 ≥12k token，任一满足即跑。已取消原"距上次 ≥10 分钟"的时间下限
- 增量：只喂未覆盖消息；全量回扫必须显式 `--backfill`
- 预算：单次 20k / 常规会话 80k / 回扫 300k / 单日 500k，**超了停在未审**（不丢、下轮续），降级记在运行账本
- 后台调用只花 API 额度，不占对话上下文窗口

### 5.2 模型档位

**沿用推理模型，不降档**（2026-11-11 决议，维持 TRIGGER_PLAN §十七 决议 1）。

TRIGGER_PLAN 内部那个矛盾（§4.6 诊断"成本主因是推理 token"、缓解措施写"用最低档位"，§十七 决议 1 又写"保留推理模型"）这样收口：**砍掉的是"独立扫描那一趟"，不是模型档位。** 一段式之后同一批内容只推理一遍，推理 token 的浪费已经从结构上消掉了；再把档位降下去，动的是抽取质量本身——而抽取质量是这条管线唯一的产出。

风险与对策：

- 沿用推理模型 + 取消时间下限，意味着活跃会话里跑得比原来频繁。**总量仍由预算兜住**（单次 / 会话 / 单日三级，超了停在未审），但会话预算会烧得比原来快
- 若验收 §七#2（总 token ≤ 两段式 60%）不达标，按顺序试这三个杠杆，**降档排最后**：① 调批次体积（30 条 / 12k token 阈值）② 提高 prompt 缓存命中（§5.2.1）③ 才考虑模型档位
- 校准工具保留档位对比能力（同一批跑两档比召回），但**不作为默认路径**

### 5.2.1 提示词必须字节级稳定（吃 prompt cache）

抽取 prompt 的规则部分（三轴、价值分级、正反清单、8 类型定义、逐字保留清单、few-shot）约 3–5k token，**每批都重发一遍**。模型厂商对重复前缀的收费远低于新内容——billion-context 靠 append-only + 瞬时消息不持久化拿到 **94% 缓存命中**。

硬要求：

- system prompt **只放稳定内容**，字节级不变：不含时间戳、批次号、会话 id、运行序号
- 变化内容（本批消息、已有主题清单、已知卡片摘要、只读上下文）全放 user message，且顺序固定
- 运行时信息（如剩余预算）也放 user message 末尾，绝不进 system
- 校准工具加一项检查：连续两批的 system prompt 哈希必须相同

### 5.3 失败与降级

| 情况 | 处置 |
|---|---|
| JSON 解析失败 | 同批重跑一次（温度 0）；仍失败 → 标 `degraded`，**消息不算已覆盖**，下轮重试 |
| 缺 `drops` 且缺 `no_value` | 重跑一次；仍缺 → 记账 `drops_missing`，**卡片照收**（不因审计缺失丢知识） |
| 单张卡准入被拒 | 进 `errors.log` 可捞回，不影响同批其他卡（沿用现有 `lib/admission.ts`） |
| `quote` 与原文不逐字一致 | 准入规则 G4 拒（现有机制，无需新增） |
| 超预算 | 停在未审，下轮续 |
| `need_context` 非空（二期） | 本批先落已达标的卡，回读批次单独跑 |
| 压缩 fail-safe 断言不过（§3.1.1） | 该条工具结果原样透传，记 `compress_fallback` |

**veto 边界（重要）**：重跑只针对**格式不合格**（JSON 解析失败、缺 `drops` 且缺 `no_value`）。模型明确给出 `no_value: true`、或空 `cards` + 完整 `drops` 时，**这是模型在行使否决权——绝不重跑、不追问、不调温度**。否则等于逼模型硬凑卡片，drop 账就变成橡皮图章。billion-context #2228 的原话："the model gets a **real veto** instead of an instruction with a checklist attached"，且答 no 之后 "resets the counter and never falls back"（只有 EMERGENCY 档绕过）。

## 七、验收标准

拿同一批历史会话（含 855 条那个）跑一段式，与两段式的既有产物对比：

| # | 标准 | 阈值 |
|---|---|---|
| 1 | **P0 探针召回（验收主指标，2026-11-12 升级）** | 全中；未命中必须逐条查清是「有归属的显式丢弃」还是「静默漏检」。探针数 ≥10，覆盖口径定义/纠正/决策/范围约束/操作纠正五类并分布在会话早中晚 |
| 2 | drop 记账覆盖率 | 每批都有 drops 或显式 `no_value`，**且每条 user 消息都有归属**（进卡或进 drop）；代码兜底补账 `autoDropped` = 0（>0 说明模型在静默忽略用户消息） |
| ~~3~~ | ~~单会话 token 总成本 ≤ 两段式的 60%~~ | **作废（2026-11-12 决议）**：实测 116%，但已明确"不考虑成本与速度"，本条不再作为验收项 |
| 4 | ~~**P1 卡片逐字接地合格率 ≥90%**~~ → **已决（2026-11-12）：取消数值阈值**。改为看 `quote_verified:false` 标记数 + #5 人工盲评 | 实测不合格的 7 张卡，数字与事实全部逐字可溯，模型改写的只是连接词——要求整串逐字等于惩罚提炼本身 |
| 5 | **盲评摘要率**：人工看 20 张卡片，判"这是知识"还是"这是摘要" | 摘要比例 ≤ 10% |
| 6 | 准入通过率 | 不低于两段式（下降说明 prompt 接地约束松了） |
| 7 | system prompt 跨批哈希一致率 | 100%（否则 prompt cache 白搭，§5.2.1） |
| 8 | 压缩 fail-safe 断言通过率 / `compress_fallback` 比例 | 通过率 100%；fallback 比例 <5%（偏高就调大上限） |
| 9 | **摘抄率**分布（正文碎片在 `msg_range` 原文中的逐字占比，见 §4.2） | 中位数 <40%；被闸门拦下的比例 <10%（偏高说明 prompt 提炼约束不够） |
| 10 | **工具事件进得来的比例**（2026-11-12 新增） | dsh 会话里 `tool/result` 事件数 = 解析出的 `role:toolResult` entries 数；助手消息里的 `tool-call` 块 100% 被序列化。这条是 §3.1.4 两个 bug 的回归防线——它们曾经让整类内容静默消失，而所有其他指标看起来都正常 |

第 5 条是专门测 summary 偏移的，不可省——它是这个设计最大的风险点。

**#4 为什么量错了（2026-11-12 操作型会话实测）**：那轮 54 张卡里 7 张 quote 不是逐字（87%，不达标）。逐张核对下来是同一个模式——**模型改写的是连接词和自己的叙述，事实与数字全是逐字的**：7 张卡 quote 里的每一个数字都能在原文找到，其中一张 4 个分片全部逐字命中、只因整串匹配失败被误标。知识卡片本来就不该是逐字转录，要求整串逐字等于惩罚"提炼"这个动作本身。

同轮还试了一个更对路的机械检查——把 54 张卡里的 **344 个数字、111 条路径**拿去原文逐字找（事实编造率）。**结论：模型编造 0 处；但检查器自己报了 16 处嫌疑，人工核对后 16 处全是分词问题**（语料库名"中国-1""中国-2"紧跟百分比被黏成 `中国-182%`；`C3/C5`、`grep/tail`、`2s/4s` 这类斜杠列表被当成路径；归一化去空格把 shell 命令和路径黏在一起）。所以这个指标方向对、实现还不能当验收标准用，**误报率远高于模型的编造率**。

**#1 应升级为验收主指标（2026-11-12）**：跨轮方差实测显著（同会话同代码两次跑，探针命中项、落库张数、降级张数、非逐字张数全都不同，见 §八 #10），单轮的任何比率都不能当结论。**只有探针召回跨轮可比**——操作型那轮已按 15 个探针执行，命中 14、唯一未命中那条被显式判「已有重复」丢弃（有归属），按归属算是 15/15。

## 七bis、实测 A/B：一段式 vs 两段式（2026-11-11，同会话同 5 批）

同一条会话（session-9583，待审 288 条 / 5 批）、同一模型、同样 `--dry`，两条路各跑一遍：

> **⚠️ 本节数据的前置条件（2026-11-12 补）**：这轮 A/B 跑在 §3.1.4 两个输入 bug 修复**之前**，两条路都看不见工具调用与工具结果（待审 288 条、原文 98k 字符、5 批）。
> 修复后同一会话是 **525 条 entries、635k 字符、18 批**，所以本节的绝对 token 数**系统性偏低**，只反映"纯文本子集"上的相对关系。
> 相对结论（一段式输入更省、输出更贵、空批次没有便宜出口）不受影响——两边瞎得一样。修复后的真实成本以 `extract-calibrate.ts` 的产物为准。

| | **一段式（新）** | **两段式（旧）** | 差异 |
|---|---|---|---|
| 输入 token | 37,431 | 51,233 | **−27%** ✅ |
| 输出 token | 138,135 | 100,662 | **+37%** ❌ |
| **合计** | **175,566** | **151,895** | **+16%** ❌ |
| 耗时 | 1108 s | 724 s | **+53%** ❌ |
| 落库卡片 | 14 | 18 | −22% |
| 提出卡片 / 候选 | 17 | 46 | 一段式自筛更严 |
| 准入被拒 | 3（全是 G4 无接地） | 5 | — |
| drop 记账 | 38 条（带判定轴） | 23 条（只有理由） | ✅ 更完整 |
| 输出/输入比 | **3.69** | 1.96 | 思考量相对输入翻了近一倍 |
| 格式重跑 / 申请回读 / fail-safe 透传 | 0 / 0 / 0 | — | ✅ 契约与压缩都稳 |

**§一 预期的"降到 50–60%"，实测是 116%。成本前提被推翻。**（n=1 时测到 +34%，n=5 收敛到 +16%，说明第一批确实偏高，但方向没变。）

### 根因：空批次在一段式里照样付全款

逐批输出 token（差分）：

| 批 | 一段式 出卡 | 一段式 out | 两段式 候选 | 两段式 out |
|---|---|---|---|---|
| 1 | 7 | 36,727 | 0 | **3,092** |
| 2 | 0 | 23,391 | 13 | 31,211 |
| 3 | 0 | 24,195 | 15 | 23,583 |
| 4 | 6 | 33,931 | 15 | 35,608 |
| 5 | 4 | 19,891 | 3 | **7,168** |

第 1、5 批：两段式的扫描发现"这批没货"就**不调抽取**，只花 3k / 7k 输出；一段式没有这个便宜出口，**即使最后出 0 张卡（第 2、3 批）也照样烧掉 23–24k**。

第 2、3 批的差额（一段式 47.6k，两段式在没货批次上只有 3–7k 量级）基本解释了整个 37.5k 的输出差距。**一句话：一段式的全部成本回退，来自"没货的批次也要按最复杂任务的规格思考一遍"。**

这也修正了 §一 对扫描那趟的判断——它不只是"花大钱买一句废话"，它同时是**一道便宜的成本闸门**：没货时把整批成本从 24k 压到 3k。真实工作里大部分批次货很少，这道闸门的价值比原评估高。

### 一段式确实拿到的东西（与几段式无关）

1. **输入 −27%**：分级压缩修订（命令/stderr 放宽、stdout 压掉、净收益检查）有效，压缩比 0.517
2. **drop 账 38 条带判定轴**：漏检第一次可见；两段式只有 23 条光理由
3. **格式重跑 0**：输出契约（缺账判不合格）5 批全过
4. **申请回读 0**：模型一次都没要求看原文 → §3.4 按需回读可以继续押后
5. **fail-safe 透传 0 条**：没有一条报错行在压缩中丢失

这五项里，只有第 3、4 项是一段式独有的；第 1、2、5 项都能移植回两段式。

### 结论与四个方向

| 方向 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | **默认改回两段式**，把一段式的收益移植过去：`lib/compress.ts` 替换 `serializeForScan`（输入 −27%）、抽取阶段的 `dropped` 落盘成 drop 账、准入接上重合度闸门 | 小，全是已有代码接线 |
| B | 保留一段式但瘦身：drop 只记价值候选、few-shot 砍到一对、prompt 精简到 5 节，目标把单次思考压回 10k | 中，且不一定压得下来（开放任务的思考量不由 prompt 长度线性决定） |
| C | 一段式 + 降模型档位 | 与"沿用推理模型"决议冲突，需重议 |
| D | 混合：先用便宜的非推理模型跑一趟"有没有货"的二分判断，有货才用推理模型跑一段式 | 等于把扫描又造回来了，只是换成廉价档 |

方向 D 值得记一笔：它承认了"便宜闸门 + 贵干活"这个结构本身是对的，只是闸门不该用推理模型。这与 §十一 架构复盘里"用推理模型单独跑一趟扫描"是过度设计的判断并不矛盾——**过度设计的是"用推理模型跑闸门"，不是"有闸门"。**
## 七ter、修复后端到端实测（2026-11-12，18 批全跑，隔离库）

2. **被拒卡片留档**（`extract-rejected.jsonl`）：本轮只留了原因计数、内容被丢弃，导致"闸门是否误杀"无法逐条复核。留档后 review 表直接展示被拒卡片全文 + 原因，可逐张判"该拦 / 误杀"。

## 八、待拍板

> **决策记录（2026-11-12）**：以上四个方向全部不采纳。用户明确"不用考虑成本和速度问题，当前就采用一段式"。本节数据保留作为已知代价的存档：一段式贵 16%、慢 53%、卡片少 22%，其中"空批次照样付全款"是结构性的、不会因调参消失。后续若成本重新变成约束，直接从方向 A 或 D 起步，不必重新测。

**已决（2026-11-11）**：① 模型档位**沿用推理模型**，不降档（§5.2）；② 批次阈值**只用 30 条 / 12k token 两个条件**，取消时间下限（§二、§5.1）。
