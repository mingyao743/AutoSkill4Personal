## 一、先纠正一个前提：召回不能靠正则保证

上一版方案里"正则预筛 + LLM 批量"有个致命漏洞：**被正则漏掉的消息永远见不到 LLM，召回上限被正则锁死。**

所以规则要反过来：

> **正则只能决定"先看谁、怎么压缩"，不能决定"给不给 LLM 看"。**
> 每条消息最终都必须被 LLM 审一次；覆盖率可以被审计，召回上限由 LLM 决定，而不是由正则决定。

这带来一个可验证的承诺：**覆盖率 = 100%**（每条未覆盖消息都会被审，审不完就下一轮继续，绝不算作已覆盖）。

## 二、五条设计原则

1. **正则只做加速器，不做准入规则。** 它可以插队、可以标记热区，但不能让消息"免审"。
2. **覆盖水位只对"已审"消息推进。** 没被 LLM 看过的消息永远留在待审区。
3. **压缩而不是丢弃。** 为了控成本，喂给 LLM 的是压缩后的全量（每个消息都有代表），不是筛选后的子集。
4. **人工只确认产物，不确认知识卡片。** 知识卡片层没有人；人看的是技能草稿和抢救摘要卡。
5. **成本有预算、失败可见。** 超预算就停在"未审"，下轮继续；不静默丢。

## 三、总架构

```
新消息
  │
  ├─ 覆盖水位：只取"未审"区间 ──────────────────────────┐
  │                                                    │
  ├─ 压缩序列化（每条消息都有代表，tool 结果截断）        │
  │                                                    │
  ├─ 抽取触发机制（LLM 批量过目）──→ 候选(msg_id + kind + 理由)  │
  │      ↑ 正则只给"热区"插队，不做排除                  │
  │                                                    │
  ├─ 知识抽取（LLM，仅候选）──→ 知识卡片(origin=signal)          │
  │                                                    │
  └─ 水位推进到"已审"位置；未审部分留给下一轮 ───────────┘

任务边界 → 终采（只抽未覆盖尾巴）→ 知识卡片(origin=harvest)
compaction → 只抽未覆盖缺口 → 知识卡片(origin=rescue, quarantine)
```

## 四、抽取触发机制：LLM 看压缩后的全量

### 4.1 输入怎么压

| 消息类型 | 喂给抽取触发机制的内容 | 理由 |
|---|---|---|
| 用户消息 | 全文（≤2000 字） | 信号主产地，不能压 |
| 助手消息 | 该轮**最终回复**的全文 + 中间消息首尾各 **500 字** | 实测平均 141 字、仅 3% 超过 1000 字 → 500+500 基本等于不截断 |
| 工具结果 | 首行 + 状态（成功/失败）+ 长度 | 数值/报错在首行，正文是噪音 |
| 工具调用参数 | **前 80 字** | 只保留"跑了什么"；实测原始参数占 397k 字符，是序列化的大头 |

压缩后大约是全量的 **25–35%**，但**每条消息都有代表**——不存在"完全没被看到"的消息。

### 4.2 正则的角色

只做两件事：

- **插队**：命中纠正/决策/工件等强信号的消息，放进当前批次的开头，必要时单独成批（小批、快出结果）
- **标注**：给消息打 `hot` 标记，让 LLM 优先判断

**不参与"是否送审"**。一条 `cold` 消息照样会进批次，只是排在后面。

> **2026-11-11 决议：插队/热区保留位不实现，正式放弃。** 现行代码召回链路零正则。理由：覆盖率承诺（每条一辈子必审一次）已保证不插队也不丢，插队只是延迟优化；用户纠正天然靠近队头，边际收益小。正则的现役岗位只剩准入规则的敏感信息拦截（确定性模式匹配，与召回无关）。§4.4 的 `hot_hit/cold_found` 留作校准期的实验记录。

### 4.3 抽取触发机制输出

```json
{"candidates":[{"msg_id":"...","kind":"correction|decision|verified|artifact","reason":"≤50字"}]}
```

只输出判断，不输出知识内容——控制输出 token。

### 4.4 召回审计（这是对"如何保证全"的正面回答）

每轮记录：

| 指标 | 含义 |
|---|---|
| `coverage` | 已审消息 / 未覆盖消息（目标 100%） |
| `hot_hit` | 正则标 hot 且被 LLM 判为候选的比例 |
| `cold_found` | **正则没标 hot，但 LLM 判出候选的比例** |

`cold_found > 0` 就证明了"正则准入规则会丢知识"，这正是本方案存在的理由。这个数字持续接近 0 时，才可以考虑提高正则权重；否则永远保持全量过目。

### 4.5 实测校准（855 条消息的真实会话）

| 角色 | 原始字符 | 抽取触发机制输入 | 占原文 |
|---|---|---|---|
| 用户 | 1,774 | 1,774（全文） | 0.4% |
| 助手 | 48,947 | 44,789（500+500） | 11% |
| 工具结果 | 361,282 | 52,907（首行+状态） | 13% |
| 合计 | 412,003 | **99,470（24%）** | |

- 助手消息平均 141 字、仅 3% 超过 1000 字 → 500+500 基本等于不截断，覆盖无损
- 用户消息只占 0.4%，但信号密度最高 → 全文送审几乎不花钱
- 成本主要来自工具结果首行（13%）→ 压缩重点在这里，不在助手消息

**同一会话的正则召回实测**：38 条用户消息，正则只命中 1 条（3%）。人工复核至少有 7 条实质性反馈被漏掉：

| 漏掉的用户消息 | 类型 | 正则为什么漏 |
|---|---|---|
| "还是不行，你深度review一下" | 负反馈 | 词表只有"不对"，没有"不行" |
| "对的，但是中文无法展示" | 转折 | 没有"但是" |
| "当前设计我只能AD, 但是重点在斜上方" | 修正 | 无否定词 |
| "1. 隐性 2. 容错 3. 根据真实世界的来" | 领域口径 | 无信号词 |
| "体力空了也能走？" | 预期违背 | 疑问句 |
| "扛货时，左右保持平衡，这能不能作为一个主要操作" | 设计决策 | 疑问句 |
| "一次做 并且做完后code review一下" | 流程约定 | 无信号词 |

这就是"正则不能当准入规则"的直接证据：**真正有价值的反馈往往不带否定词。**

### 4.6 实测校准（2026-11-11，855 条消息的真实会话）

**召回**

| 指标 | 结果 |
|---|---|
| 批次 | 22 批（≤40 条 / ≤12k 字符） |
| 候选 | 251 条（179 个唯一 msg_id，72 条重复，需按 msg_id 去重） |
| 用户消息命中 | 22 / 38（58%） |
| 正则漏掉的 7 条已知信号 | **7 / 7 全部命中** |
| kind 分布 | decision 95 · verified 76 · domain 40 · other 19 · artifact 12 · correction 9 |

**成本（实测，不是估算）**

| 项 | 实测 |
|---|---|
| 序列化 | 845 行 / 187,502 字符 |
| 输入 token | 79,467 |
| 输出 token | **156,122（输入的 2 倍）** |
| 总耗时 | 约 10 分钟（22 次调用） |

输出成本失控的原因：**推理型模型的思考 token 计入 completion**。有一批只标了 11 条候选却产生 31,333 输出 token。

修正措施（写进实现）——**2026-11-11 复核后的状态**：第 1 条作废，第 2、5 条随两段式取消而失效，第 3 条已修订，第 4 条保留。

1. ~~抽取触发机制用**非推理模型或最低思考档位**，并设 `max_tokens` 上限~~ → **作废**：档位沿用推理模型；成本改从"砍掉独立扫描那一趟"省，不从档位省
2. 输出压到最小：`{"msg_id":"…","kind":"…"}`，理由不逐条写 → **失效**：一段式没有候选中间态，直接出卡片 + drop 账
3. **工具调用参数只留前 80 字**（实测它占了序列化的一半：原始 397k 字符）→ **已修订**：命令行/代码块放宽到 600 字、stderr 800 字，JSON/YAML 大参数仍留前 80 字（ONE_STAGE_EXTRACT §3.1）
4. 按字符分批（12k）而不是按条数（40），减少调用次数 → **保留**：现为"待审 ≥30 条 **或** 压缩后 ≥12k token"，时间下限已取消
5. 候选按 `msg_id` 去重后再抽取 → **失效**：无候选中间态，去重落在准入与落库

目标：单会话 ≤60k token。

### 4.7 agent thinking 怎么用（分层）

实测该会话的内容构成：

| 内容 | 字符 | 占比 |
|---|---|---|
| thinking | 702,076 | 47% |
| 正文（text） | 406,759 | 27% |
| 工具调用参数 | 397,402 | 26% |

**AutoSkill 现在完全不用 thinking**：`serialize.ts` 明确丢弃，`window.ts` 的字符估算也不计入。

不用它是对的：thinking 是模型自己的推演（P3 级），未验证、会自我推翻、体量巨大。但代价是丢掉了两类关键材料——**C2 的"被否路径"**和 **C1 的"错在哪"**，因为模型最初的错误假设就写在 thinking 里。

采用分层策略：

| 层 | 用不用 thinking | 理由 |
|---|---|---|
| 抽取 / 抽取触发机制 | ❌ 不用 | 成本 + 不可信 |
| **编译** | ✅ **按需回捞** | 当某条知识卡片要写进"判断/被否方案"时，按 `msg_range` 取那几条消息的 thinking（每段 ≤500 字、最多 5 段），作为决策证据 |
| 质量判断 | ❌ 不用 | 避免用模型自己的推演给自己打分 |

宿主差异：pi 会持久化 thinking（实测 334 块）；dsh 是否持久化待查证，拿不到就静默降级。

## 五、成本与预算

**决议后的成本模型**：抽取触发机制保留推理模型 + 逐条理由，所以输出成本不降；只通过"工具参数 80 字 + 按字符分批"降输入。

| 场景 | 输入 | 输出 | 合计 |
|---|---|---|---|
| 全量回扫（855 条，一次性） | ~56k | ~156k | **~212k** |
| 常规会话（200 条，稳态） | ~13k | ~36k | **~49k** |
| 单次增量（40 条/批） | ~2.5k | ~7k | **~10k** |

关键机制：**增量扫描 + 显式回扫**。

- 默认只扫"未覆盖"的新消息，每条消息一辈子只被看一次
- 全量回扫是**显式命令**（`--backfill`），不是自动行为
- 这样推理模型的高输出成本只发生在增量上（每次约 10k），不会每轮重扫整个会话

预算护栏：

- 单次运行上限 **20k token**，超了停在未审
- 单会话常规上限 **80k**；全量回扫上限 **300k**（超了分批跑，可中断续跑）
- 单日上限 **500k**，超了降级为"只审用户消息 + hot 助手消息"，记录 `degraded`
- 批次：**≤12k 字符**（不按条数切）

**关键澄清**：后台调用只花 API 额度，不占对话上下文窗口。

## 六、知识抽取

- 触发：候选 ≥5 条 / 任务边界 / 会话退出 / 压缩前
- 输入：候选消息的**原文**（不是压缩版）
- 输出：知识卡片（走 `admission` 的类型/why/去向，`origin=signal`）
- 幂等：同一 `msg_range` 不重复抽取；知识卡片 id 仍由内容+来源派生

## 七、任务边界终采

- 触发：用户表示完成 / 切新任务 / commit / 长时间空闲 / `session_shutdown(quit)` / 显式 `kb_harvest`
- 范围：**只抽未覆盖的尾巴**（覆盖派生，不重扫全session）
- 状态：draft，`origin=harvest`

## 八、compaction 抢救：降级为兜底

- 只处理未覆盖区间（别人管过的缺口不碰）
- 产出 `origin=rescue`、`status=quarantine`（不再 `published`）
- **不参与技能编译**，只做两件事：
  1. 作为压缩摘要的证据（摘要里可引用）
  2. 进入"抢救摘要卡"等待产物级确认

### 抢救产物怎么让人确认（对应"人确认产物"）

压缩时生成一张 **1–3 行的抢救摘要卡**：

```json
{"kind":"rescue-digest","session":"…","saved":12,"highlights":["…","…"],"atom_ids":["…"]}
```

- 不打断压缩流程，异步进"待确认队列"
- 用户下次空闲时**整卡确认/丢弃**（一次点击级别，不是逐条知识卡片）
- 确认后：卡内知识卡片晋升为 `harvest` 级，可进编译
- 丢弃后：知识卡片留在池里但不进技能

这样人确认的是**一张卡**，不是几十条知识卡片；而且发生在空闲时，不在压缩等待时。

## 九、信任分级

| 来源 | origin | 初始状态 | 进技能编译 | 晋升路径 |
|---|---|---|---|---|
| 知识抽取 | signal | draft | ✅ 优先 | — |
| 任务终采 | harvest | draft | ✅ | — |
| 手动回填 | backfill | draft | ✅ | — |
| 压缩抢救 | rescue | quarantine | ❌ | 抢救摘要卡确认 / 后续同知识复现 |

编译选材顺序：`signal > harvest > backfill`；`rescue` 必须晋升后才参与。

## 十、人工确认只发生在两处

| 位置 | 确认什么 | 频率 | 时机 |
|---|---|---|---|
| 技能草稿 | 编译产物的正文 + 描述 | 每主题一次 | 空闲 |
| 平台发布 | 变更 diff + 影响 | 每次发布 | 由平台二次确认 |

**知识卡片层没有任何人工确认**。这是刻意的：知识卡片数量大、单条信息量小，逐条确认只会产生橡皮图章。

| 3 | 会话文件 stat（size/mtime）变化后读尾部 | 中 |
| 4 | 仅 capture + compaction 兜底 | 低 |

**已知限制**：dsh 覆盖率会低于 pi，统计指标必须按宿主分开看，不能混在一起判断。

## 十二、可观测

新增 `runs.jsonl`，每次运行一行：

```json
{"ts":"…","kind":"trigger-scan|knowledge-extract|harvest|rescue","session":"…","harness":"dsh",
 "covered":40,"reviewed":40,"candidates":6,"atoms":5,"rejected":1,
 "degraded":false,"tokens":12345,"error":null}
```

核心指标（按宿主分开）：

| 指标 | 目标 | 告警 |
|---|---|---|
| coverage | 100% | <95% → 预算不足/任务中断 |
| signal 占编译知识卡片 | ≥60% | <40% → 抽取触发机制或知识抽取没跑 |
| rescue 占编译知识卡片 | ≤10% | >20% → 另外两条路又断了 |
| cold_found | 观测值 | 持续为 0 可调低正则权重 |

## 十四、迁移

- 存量 453 条不动；`origin` 对旧知识卡片按 `extracted_by` 推断
- 存量 rescue 知识卡片不回溯降级（避免现有技能突然失效），但**新编译的技能不再吃它们**

## 十五、验收

1. 一次真实长会话：coverage = 100%，`cold_found` ≥ 1（证明正则准入规则确实会漏）
2. 压缩时 rescue 只处理缺口，产出显著少于改造前
3. 编译进技能的知识卡片：signal ≥60%、rescue ≤10%
4. 抢救摘要卡能整卡确认/丢弃，确认后知识卡片才可进编译
5. 预算超限时停在"未审"，下次继续，不丢消息
6. 无 LLM 配置时下次会话有明确提示，不静默

## 十七、决议（2026-11-11）

| # | 决策 | 影响 |
|---|---|---|
| 1 | **抽取触发机制保留推理模型** | 输出成本维持在 ~156k/855 条；靠"增量 + 显式回扫"控制总账，不靠换模型 |
| 2 | **候选逐条写理由** | 便于人工复核与后续调试；理由 ≤30 字，实测平均正好 30 字，不是成本主因 |
| 3 | **工具参数只留前 80 字** | 序列化 187k → ~131k，输入降约 30% |
| 4 | **抢救摘要卡放下次会话首轮提示** | 与现有 `pendingNotice` 合并，不新增入口 |

由此确定：

- 抽取触发机制的批次单位改为 **≤12k 字符**
- 成本主因是**推理 token**，不是输入；因此优化的方向是"少跑几次、每次覆盖更多"，而不是"少看消息"
- 全量回扫必须显式触发，避免新装用户第一次会话就烧掉 200k token

剩余可调项（不影响决议，先按默认实现）：

- 是否给抽取触发机制传 `reasoning_effort: low`（仍是推理模型，只是思考更短）——默认**不传**，保持模型默认档；若实际成本超预算再开
