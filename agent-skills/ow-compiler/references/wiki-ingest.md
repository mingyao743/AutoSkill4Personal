# 写作细则

## 标题

名词短语，能单独看懂。

| ✅ | ❌ |
|---|---|
| qdoc MCP 参数命名 | 关于参数的一些问题 |
| 两级锁的设计理由 | 锁 |
| 平台搜索是短语匹配 | 搜索相关 |

「关于…」「…相关」「…的问题」这类前缀全部删掉，它们不携带信息。

## 摘要

一句话，≤200 字，说清**这页能回答什么问题**。

- ✅ 「平台工具用 doc_id / content_md / base_version，不是直觉的 document_id / content / version」
- ❌ 「本文介绍了 qdoc MCP 的参数命名规则」（没说规则是什么）

摘要会进平台搜索的索引，写得含糊就搜不到。

## 正文开头

一段话，说清：这页讲什么、什么场景下用得上。

```markdown
qdoc.chat 的 MCP 工具 schema 与直觉不一致，第一次调用必然踩坑。
本文记录实测到的参数名与两个隐藏约束。
```

不要写「本文将介绍…」这类元叙述——直接说内容。

## 表格 vs 列表 vs 段落

| 内容 | 用什么 |
|---|---|
| 多个对象的同一组属性 | 表格 |
| 有序步骤 | 有序列表 |
| 无序要点（≤5 条） | 无序列表 |
| 因果、理由、权衡 | 段落 |
| 代码、命令、配置 | 代码块 + 语言标记 |

**一个判断**：如果这页读下来只有标题和列表，说明你其实没把话说完整。补一段解释。

## 代码块

必须带语言标记，否则平台渲染时没有高亮：

````markdown
```ts
const x = 1;
```
````

命令行用 `bash`，配置用 `json` / `yaml`，报错原文用 `text`。

## 长度

| 页类型 | 合理长度 |
|---|---|
| 单条事实（references/） | 200–500 字 |
| 踩坑记录（concepts/） | 300–800 字 |
| 操作流程（skills/） | 500–1500 字 |
| 选型对比（synthesis/） | 800–2000 字 |

超过 2000 字基本可以拆成两页。

## 不要做的事

| 不要 | 因为 |
|---|---|
| 写 `# 一级标题` | 标题由 `title` 字段给，重复了 |
| 写 frontmatter | 编译器会加 |
| 写「本文」「本节」 | 元叙述，不携带信息 |
| 编造 wikilink 目标 | 发布后变死链文本 |
| 复制整段代码 | 只留关键的几行，其余说明「见某文件」 |
| 用「显然」「众所周知」 | 这是在掩盖没验证 |
